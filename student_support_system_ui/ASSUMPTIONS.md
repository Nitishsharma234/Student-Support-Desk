# Assumptions

- **Team mapping**: the CSV's assumed "Student Services" team (if present in the real dataset) is merged into **Administration**, since the brief lists exactly Accounts / Academic / Administration / Discipline as the fixed destinations plus a catch-all. `Other` routes to a `General Support` team so every ticket always has a valid destination.
- **SLA hours are fixed by category, not learned**: Fee 24h, Attendance 12h, ID Card 48h, Documents 48h, Certificate 72h, Discipline 4h, Other 72h. These are business rules, not model output — the brief asks for SLA *calculation*, and a learned SLA would leak from post-hoc outcome columns (see ML_REPORT.md).
- **"At Risk"** = less than 25% of the SLA window remaining and not yet breached. This threshold isn't specified by the brief; 25% was chosen as a reasonable early-warning margin and is a single constant in `core.sla_info` if it needs tuning.
- **Auto-escalation is triggered on demand** (`POST /api/admin/auto-escalate`, exposed as a manager button), not on a background scheduler/cron — the brief doesn't specify a scheduler and adding one (APScheduler, Celery, etc.) would be exactly the kind of unnecessary infrastructure the brief says to avoid. A real deployment would wire this endpoint to a periodic job.
- **Escalation raises priority by one level and cannot be applied twice**: a ticket already `Escalated` or already in a final state (`Resolved`/`Closed`) is rejected with `409`, which is the duplicate-escalation guard.
- **Student identity = username**: the brief asks for "Roll Number + password" login; the seeded student usernames are already roll-number-shaped (`STU23BCSE0001`) and the login form labels the field "Roll number" for the student role. There's no separate roll-number field distinct from username — they're treated as the same identifier, since introducing a second identity field wasn't asked for and isn't needed for the workflow.
- **Low-confidence / missing-model tickets default to `Other` / `Medium`** and are flagged `needs_review` for a human to confirm, rather than guessing — this satisfies "low-confidence predictions require manual verification" without inventing a confidence score when no model is loaded at all.
- **Ticket ID format**: `TKT-<year>-<5-digit sequence>`, generated from an atomic MongoDB counter — chosen for human readability and to guarantee uniqueness without relying on Mongo `_id`.
- **No file attachments**: the brief's workflow doesn't require attachment upload/storage, and the schema only needs an `attachment_present` flag as a model feature, so no file storage layer was added (kept in scope, per "no unnecessary features").
- **Feedback/satisfaction score** is only collectible by the student, only after the ticket reaches a final state, and only once (no field to overwrite it once set is exposed) — a natural implication of "resolution" being the point at which a student can judge the resolution.
